# Architecture options — proposal, not an approved environment

## Decision to review

Recommend a **one-shot, individually identified Linux/amd64 VM with its own Docker daemon**, controlled by a trusted in-guest controller and an external supervisor. This is a candidate design, not an assertion that such a VM, provider, privileges, independent reviewer or exclusivity already exist. It is `BLOCKED` until [decision-record.md](decision-record.md) is completed, reviewed and signed by both owners. No existing Docker Desktop daemon, candidate, hidden material or paid service is touched in D0.

| --- | --- | --- | --- |
| Security boundary | Dedicated guest kernel and virtual disks, separate guest daemon; hypervisor/provider administrators remain trusted. Prefer the tested rootful-in-VM profile; root inside VM is a powerful trusted principal, not candidate access. | Rootless changes semantics; Docker documents that cgroup flags may be ignored without required cgroup v2/systemd setup and CPU may not be delegated. ## Candidate design and trust boundary

- A trusted provisioner creates a fresh, one-shot Linux/amd64 guest from a pinned approved image, with a private virtual disk, independently capped capacity and memory, and no automatic mounting, clipboard, Docker Desktop socket, host filesystem, shared credentials, private candidate, Oracle, hidden inputs or reference service. One guest runs one predeclared execution, one fault at a time.
- The guest's local trusted controller invokes the pinned Docker CLI against the guest's exact Unix socket. It has no reason to reach a workstation socket or a remote endpoint. Since [command()](../../packages/target-worker/src/controller.mjs#L65) currently inherits its environment and runs `docker` without an explicit endpoint argument, a future trusted launcher must clear/allowlist environment and CLI config, bind the exact approved executable/socket and fail closed against context or host fallback. No such launcher is implemented here.
- Candidate code runs only within the existing restricted container profile, never in the host or trusted controller. The candidate has no Docker socket, host mount, network, credentials, Oracle, hidden corpus or writable trusted evidence. The trusted observer, controller and fault actuator are separate from the candidate; fault helpers must not provide candidate-controlled privileged execution. Any new privilege or change to a shared trust boundary requires both-owner authorization.
- The external supervisor is outside the guest's failure domain and can stop/quarantine the **exact approved VM** through a scoped out-of-band hypervisor/provider path when the guest daemon, CLI or controller hangs. It has a bounded watchdog, a separately secured append-only attempt/lease log, and a tested evidence-preserving recovery path. It is not merely another promise, process or timer in the injected daemon. Whether a specific provider offers these guarantees is `PENDING`; a cloud provider or spend is not selected or authorized.
- The narrowly authorized fault actuator has a closed operation allowlist and one active case; no global prune, wildcard/name-prefix deletion, arbitrary container command, workstation daemon, host mount, secret access or hidden data. A synthetic same-prefix sentinel belongs to the test environment and carries a different run/owner identity; it is not a real foreign production resource. The G0 finalizer must never modify it.

The proposed operation gate is a trusted, isolated socket relay/launcher, not a raw Docker socket exposed to candidate code. Before forwarding a mutation it records a unique operation ID and endpoint/target in an externally observed write-ahead journal, permits only an approved method and exact run target, and retains the upstream request state even if the original CLI disconnects. It serializes conflicting mutations and distinguishes long-lived attach streams from state-changing requests. A finalizer may be admitted only when every earlier mutation has a verifiable terminal upstream outcome **and** operation-specific daemon state is reconciled against the exact ledger. A mere closed client socket, a missing response, a restarted relay, a disappeared daemon or an empty list is not a terminal outcome; these lead to quarantine. The exact Docker API semantics and ability to maintain this barrier for each method still require implementation and engine testing. If they cannot be demonstrated without weakening the existing trust boundary, D1/D2 remain blocked.

## Exclusivity over the complete lifetime

An empty initial inventory or a differently named Docker context is not proof. Require all of the following, from provisioning through terminal evidence capture and approved teardown:

1. **Exclusive lease and identity.** Provider/hypervisor records bind a one-shot VM ID, boot/instance ID, virtual disk/network IDs, daemon process/socket identity, approved operator and supervisor to a single time-limited lease. List every principal with hypervisor, guest-root and socket authority; deny all others for the full window. No shared socket, host integration or alternate unmonitored control plane. Explicitly record privileged-provider/admin access as a trust assumption, not a cryptographic impossibility.
2. **Prevent competing writers.** Controlled guest boot and service configuration start only reviewed, pinned services; socket and filesystem ownership/ACLs admit the trusted controller alone. Restrict or disable extra login channels and automation. Do not attach external clients or credentials. Set an exclusive management-plane lease and prevent parallel jobs. A client restricted only by voluntary convention does not qualify.
3. **Observe continuously, independently.** Supervisor records VM lifecycle, lease/ACL changes, authenticated management actions, daemon/socket identity and bounded guest/host audit telemetry with monotonic timestamps; retain continuity/heartbeat and gap alarms. Correlate full pre/post container, volume, network and image inventories with approved mutations and exact IDs; keep raw records private. Docker event streams are supplementary, not complete proof: Docker documents a limited retained event history. An observer gap, unaccounted admin action, changed identity, unexpected client or inventory drift stops the attempt.
4. **Prove quiescence before independent cleanup.** On timeout or abort, kill and externally observe the relevant controller/CLI process tree and establish that no daemon-side request remains active or can create or delete later. CLI death alone is insufficient. If settled state or daemon integrity cannot be established, quarantine the VM and record `ERROR/BLOCKED`; do not invoke another mutator or fabricate zero.
5. **Close the interval.** Retain complete and partial attempts and before/after inventories under restricted access; export and verify the evidence outside the guest before any preapproved disposal. Stop the exact VM, verify its identity and lifecycle state externally, then follow the approved expiry/teardown plan. A recovered or destroyed VM is not evidence of normal cleanup.

This is a conditional assurance argument, not proof against a malicious hypervisor/provider administrator or an uncompromised-looking observer that actually lost data. If privileges, monitor continuity, inventory completeness, endpoint identity, separate storage, or independently executable recovery cannot be established, readiness is `BLOCKED`. See [Docker event retention](https://docs.docker.com/reference/cli/docker/system/events/).

## Source-grounded gaps that the future design must close

- [G0Docker.call](../../packages/workshop-audit/src/g0/docker.mjs#L219) tracks underlying work promises, applies a lifetime/cleanup deadline and marks `cleanupUncertain` on a bounded cleanup rejection. [close()](../../packages/workshop-audit/src/g0/docker.mjs#L585) aborts and bounded-joins before normal cleanup. A timed-out Docker CLI may nevertheless have submitted work to the daemon; no actual engine fault behavior is asserted.
- [finalizeLedger](../../packages/workshop-audit/src/g0/finalizer.mjs#L7) reopens the ledger into a new adapter and separate sink; it is **not** a separately supervised OS process and does not share the old adapter's `pending` set. [runG0](../../packages/workshop-audit/src/g0/run.mjs#L203) attempts this finalizer after a normal close failure. Future external quiescence/interlock is therefore a prerequisite, not a property already implemented.
- `create()` saves a null-ID ledger entry before Docker create, then saves the returned full ID. `inventory()` filters by run label, reconciles null IDs using name plus run/owner/role, and requires no run-labelled volumes. `remove()` re-inspects full ID/name/labels before removal. It does **not** provide full-daemon inventory or an atomic inspect-and-remove operation. Current close/finalize can attempt revalidated exact-ID removals even after an inventory error; the proposed supervisor imposes a stricter stop on uncertainty.
- [Evidence.write](../../packages/workshop-audit/src/g0/evidence.mjs#L79) fsyncs a temporary file before rename, but does not fsync the parent directory there. File fsync and a returned `save()` alone do not establish crash-durable directory entry persistence. After interrupted create/persistence, preserve ambiguous state; do not assume an orphan belongs to the run or remove it until exact identity and authority are established.
- [Evidence.verifyEvidence](../../packages/workshop-audit/src/g0/evidence.mjs#L139) verifies the sealed trace/ledger/finalizer catalog and intentionally excludes `receipt.json`. A proposed externally witnessed receipt commitment must be separately designed; the current catalog alone is not a crash-proof independent receipt seal.
- [runG0](../../packages/workshop-audit/src/g0/run.mjs#L288) writes `receipt.json` before re-verifying both catalogs. If that subsequent verification fails, it returns an ERROR object without rewriting the already written receipt. A future consumer must reconcile the returned/terminal status and independent catalog checks; the presence or contents of that file alone are not authoritative. This is a source-derived risk, not an executed engine failure.

Option B is acceptable only if both owners explicitly approve an equivalent, independently demonstrated full-lifetime boundary and out-of-band recovery. C remains rejected for destructive injection regardless of empty inventory, labels or a renamed Docker context.
