# Proposed safety runbook — no execution in D0

This is a future operating plan, not a command to create a VM, access Docker, execute a fault or change infrastructure now. Use only after independent design review, two owner decisions on the exact design SHA, a separately reviewed implementation and a separate authorization identifying the environment and execution window. All proposed controls are `NOT_RUN`; the exact provider, identities, pins and recovery mechanism remain `PENDING` in [decision-record.md](decision-record.md).

## Roles and state machine

The provisioner controls the VM lifecycle, the trusted controller uses its own guest daemon, an outside supervisor controls only the exact VM's stop/quarantine path, and an authorized local reviewer examines raw public/synthetic evidence. The candidate controls none of them. Owner decisions cannot be delegated to a single signer.

`PENDING_DECISION → REVIEWED_IMPLEMENTATION → EXECUTION_AUTHORIZED → PREFLIGHT → BASELINE → ONE_CASE_AT_A_TIME → NORMAL_CLOSE → INDEPENDENT_FINALIZER → EVIDENCE_VERIFY → STOP/TEARDOWN` is a proposal, not a record of execution. At any state, an uncertainty or stop-loss goes to `ERROR/BLOCKED → QUIESCE_OR_QUARANTINE → INCIDENT_HOLD`. Recovery is separately recorded and cannot erase the original failure. An external supervisor must remain independent of the guest daemon, CLI and controller; its monotonic total deadline includes preflight, work, normal cleanup, finalizer, evidence export and stop.

## Preflight after explicit authorization

1. Read the two authenticated SHA-specific owner decisions and independent reviews. Confirm the approved fixture set, per-fault methods, exact finite limits, expiry, operator/supervisor/custodian, one-shot execution and no-retry rule. Missing, changed, revoked or expired authority => `BLOCKED`.
2. Verify the exact provisioner, VM/boot/virtual-disk/network identities, immutable guest and worker images, controller/evaluator/actuator/supervisor SHAs and dependencies. Verify distinct guest kernel, daemon, socket, Docker and containerd storage, network and resource allocation. Confirm there are no workstation mounts, devices, socket, credentials or other shared control paths. Record all privileged administrators and the provider trust assumption; unknown access => `BLOCKED`.
3. Install or start nothing during read-only preflight. The following are permissible **future read-only checks** against the already authorized, explicitly identified guest endpoint: version and daemon info; full, unfiltered container/volume/network/image listings; inspect exact IDs; process/service and socket ACL inventory; cgroup-v2 controllers and effective CPU/memory/PID limits; seccomp mode and kernel/runtime pins; filesystem capacity and evidence-root permissions. Record raw results only in restricted evidence. All CLI invocations must use the pinned trusted executable and explicit verified endpoint with sanitized config/environment. No default-context fallback; if endpoint identity is uncertain, do not issue the check.
4. Compare complete inventory against the approved baseline and reserved synthetic sentinel. A stopped foreign container, unknown volume, another client, mismatched owner/ID, changed daemon, shared disk, unexpected network or unexplained inventory => `BLOCKED`. Do not treat an empty filtered list as a full-daemon inventory. The fake foreign sentinel is wholly controlled by this test VM, has a distinct run/owner and is never a production resource.
5. Demonstrate that the external supervisor has exclusive lease/ACL and continuous monitoring, complete and gap-detecting observation, independent watchdog capacity and an available evidence-preserving exact-VM stop. Validate the recovery path through an independently reviewed, separately approved rehearsal; a destructive rehearsal is not authorized by D0. If control-plane audit coverage, observer continuity, daemon-side quiescence, or ability to preserve partial evidence is unprovable, `BLOCKED`.
6. Verify independent evidence destination and permissions, free-space reserves, quota and actual per-case/total bounds. Bind the run to guest/runtime/recipe/fixture/evaluator hashes. Predeclare the exact positive baseline, case order, triggers, monitor predicates, falsifiers and finalizer policy; no auto-retry or cherry-picking.

## Future controlled run

- Record an append-only external attempt start before launching the approved public/synthetic baseline. The trusted controller can use the daemon; the candidate has no Docker socket, privileged host access, host mount, network, keys, reference, Oracle, hidden corpus, evidence destination or authority to execute on the host.
- Only after a clean, verified baseline and complete supervisor readiness, execute each owner-approved fault in the declared order with concurrency one. At each barrier retain before/after private snapshots and independent observations. The trusted narrowly scoped helper/relay uses only fixed approved actions; it cannot expose a general privileged endpoint to the candidate.
- A transient failure of the test itself is retained as a distinct attempt. Do not repeat it automatically or select the best result. Stop on unexpected inventory, unknown ownership or unaccounted competing activity. No broad or prefix cleanup and no #134 workshop finalizer.
- Normal G0 cleanup joins original work, but the current `close()` may proceed with revalidated known-ID cleanup after an inventory failure. The proposed outer guard must stop it on uncertainty rather than claiming that stricter behavior already exists. Require verified exact run ID, owner ID, role, full container ID and name immediately before a permitted mutation. The adapter creates no volumes; unknown volumes are incidents.
- The existing independent ledger finalizer reopens a ledger in a new adapter and a separate evidence sink, but does not see the original adapter's `pending` set. Invoke any future independent finalizer only after the supervisor has proved no old client or daemon request can complete later. If this cannot be proven, quarantine and retain unknowns instead. A new independent finalizer architecture is implementation work, not delivered here.

## Stop-loss and recovery

Triggers include failed exclusivity, observer gaps, daemon/socket/VM identity drift, inaccessible supervisor or recovery, unexpected privileged client, a missing or conflicting ledger/label/ID, unknown volume, operation outside the exact approved ledger, inventory race, resource or host pressure, leaking raw evidence, cgroup enforcement failure, evidence write/seal failure and any deadline breach.

1. **Freeze useful work.** Record the trigger and monotonic time externally; withdraw new operation admission. Preserve current nonzero/unknown resource counts, partial evidence and the original finding.
2. **Determine quiescence without assuming it.** The outer watchdog observes the controller/CLI process tree and independently accounts for daemon-side outstanding actions. Killing or observing exit of a CLI alone does not establish that Docker did not create or remove an object later. No new in-guest mutator may race unresolved work.
3. **Quarantine if uncertain.** Use only the preauthorized out-of-band control for this exact VM, with the preapproved evidence-preservation sequence. If the stop mechanism or evidence export fails, retain the incident and VM under hold for the named owner/custodian. Do not access or repair the workstation Docker Desktop.
4. **Recover only under the approved recovery plan.** Once quiescence, exact ownership and authority are established, the independent recovery principal may perform only narrowly authorized operations; unknown objects are never removed. Retain pre-recovery and post-recovery inventories. Emergency removals are counted as emergency, with `ERROR/BLOCKED` sticky even if later inventory is empty.
5. **Finish the lease.** Independently verify and export the separate catalogs, receipts, supervisor log and incident evidence before the authorized exact-VM expiry/teardown. The synthetic sentinel is protected from G0 cleanup; its test-only VM may be disposed of only under the explicitly approved VM lifecycle after evidence preservation. Teardown is not normal G0 cleanup.

## Evidence custody and safe publication

Retain every complete, failed and partial attempt, including original fault, secondary cleanup/evidence faults, actual unknowns, ledger, exact identity, raw Docker observations, command/daemon outputs, monotonic timeline and the external supervisor's no-gap account. Use a controlled owner-only evidence root with POSIX `0700` directories and `0600` files, no symlink/hardlink substitution, bounded bytes and no candidate write access. Preserve private paths and raw data outside Git, PRs, chat and model context. An authorized local reviewer checks exact bytes without exporting them.

Normal and finalizer catalogs are distinct. Independently bind their contents, run/recipe/evaluator/fixture hashes, before/after inventory commitments, supervisor record and **receipt** in an externally witnessed immutable commitment. The current [catalog verifier](../../packages/workshop-audit/src/g0/evidence.mjs#L139) excludes `receipt.json`; it must not be represented as a receipt seal. The current [run lifecycle](../../packages/workshop-audit/src/g0/run.mjs#L288) can return ERROR after post-write verification fails without rewriting the previously written receipt; never promote that file without reconciling the terminal result and both catalogs. The current ledger writer fsyncs its file but does not fsync its parent directory; a crash around rename leaves durability uncertain and requires an incident/quarantine, not assumed orphan ownership. The exact durable journal/witness design is a future reviewed implementation decision; these notes do not change the existing contract.

Public output is limited to an allowlisted coarse case ID, executed/`NOT_RUN`, verified verdict and safe code if specified, identities already safe to disclose, bounds, normal/finalizer counters only when known, incident state and commitments. Raw source, Docker inspect, stdout/stderr, HTTP/DB traces, private paths, secrets, hidden inputs and raw ledgers never enter GitHub or an LLM. A public hash is not independent custody. Real two-domain G4 custody remains separately blocked under [#55](https://github.com/Meta-Project2026/Metamorph/issues/55) and [#188](https://github.com/Meta-Project2026/Metamorph/issues/188).
